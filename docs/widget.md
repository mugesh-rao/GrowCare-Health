# Area selection, countdown, and background widget — portable Tauri recipe

This is the implementation record for Capptivo's former area recorder and its
current floating voice widget. It is deliberately written as a copy/paste
specification for another Tauri 2 + React + Vite application.

## Direct answer: what renders the popup/widget?

No HTML is generated by Rust. Each popup is a **native OS `WebviewWindow`**:

```
Rust / Tauri                         Vite + React
-----------                           ------------
hotkey or command ── show/create ──> native window
                                      └─ loads `widget.html` / `area.html`
                                         └─ runs its matching TSX entry
                                            └─ renders the React UI
```

The current floating voice widget is a declaratively-created native window in
`src-tauri/tauri.conf.json`, labelled `widget`. Vite builds `widget.html`, and
that page runs `src/widget-main.tsx`, which renders `WidgetApp`. Rust toggles
the same native window with `widget.show()` / `widget.hide()` from the
`Alt+Shift+C` global-shortcut handler in `src-tauri/src/lib.rs`.

It is `alwaysOnTop`, transparent, undecorated, and skipped from the taskbar.
That is how the small orb appears above the application: it is *not* a React
modal in the main application window. React is only painting the contents of
the already-existing OS window.

Hiding or closing the **main application window** can leave the widget alive
only if the Tauri process is deliberately kept alive (hide the main window
instead of exiting). Once the application process exits, every Tauri window,
including the widget, exits too. A website/browser tab closing is unrelated to
the packaged Tauri process.

## Current widget: the smallest complete pattern

### 1. Build one HTML entry per window

Add a Vite input and an HTML file. This is required both in development and in
the packaged application; a Rust `WebviewUrl::App("widget.html")` only works
when Vite has emitted that page.

```ts
// vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import { fileURLToPath, URL } from "node:url";

const entry = (file: string) => fileURLToPath(new URL(file, import.meta.url));

export default defineConfig({
  plugins: [react()],
  build: {
    rollupOptions: {
      input: {
        main: entry("./index.html"),
        widget: entry("./widget.html"),
        area: entry("./area.html"),
        frame: entry("./frame.html"),
      },
    },
  },
});
```

```html
<!-- widget.html -->
<div id="root"></div>
<script type="module" src="/src/widget-main.tsx"></script>

<!-- area.html -->
<div id="root"></div>
<script type="module" src="/src/windows/area/main.tsx"></script>

<!-- frame.html -->
```

### 2. Declare a persistent widget window

The current project creates `widget` at app startup but starts it hidden. That
makes show/hide instantaneous. Put this in `app.windows` in
`src-tauri/tauri.conf.json`:

```json
{
  "label": "widget",
  "title": "My App",
  "url": "widget.html",
  "width": 72,
  "height": 72,
  "resizable": false,
  "decorations": false,
  "transparent": true,
  "shadow": false,
  "alwaysOnTop": true,
  "skipTaskbar": true,
  "focus": false,
  "visible": false
}
```

The widget React entry can resize its own native window while it expands:

```tsx
// src/WidgetApp.tsx
import { useState } from "react";
import { LogicalSize } from "@tauri-apps/api/dpi";
import { getCurrentWindow } from "@tauri-apps/api/window";

const IDLE = 72;
const OPEN = 320;

export function WidgetApp() {
  const [expanded, setExpanded] = useState(false);
  const win = getCurrentWindow();

  async function expand() {
    setExpanded(true);
    await win.setSize(new LogicalSize(OPEN, OPEN));
  }
  async function dismiss() {
    setExpanded(false);
    await win.setSize(new LogicalSize(IDLE, IDLE));
    await win.hide();
  }

  return expanded ? (
    <section className="widget-expanded">
      <button onClick={dismiss}>×</button>
      {/* Voice/chat/status UI belongs here. */}
    </section>
  ) : (
    <button data-tauri-drag-region onClick={() => void expand()}>
      Open widget
    </button>
  );
}
```

The widget's capability must permit the APIs it calls. Capptivo has
`src-tauri/capabilities/widget.json` scoped to `["widget"]` with
`core:window:allow-set-size` and `core:window:allow-start-dragging` (plus only
the app commands that widget is allowed to invoke). Do not grant `core:default`
to every sensitive command just because this is a separate window.

### 3. Show/hide it from Rust, including after the main UI is hidden

```rust
use tauri::Manager;
use tauri_plugin_global_shortcut::GlobalShortcutExt;

const WIDGET_HOTKEY: &str = "Alt+Shift+C";

fn register_widget_hotkey(app: &tauri::AppHandle) {
    app.global_shortcut().on_shortcut(WIDGET_HOTKEY, |app, _, event| {
        if event.state() != tauri_plugin_global_shortcut::ShortcutState::Pressed {
            return;
        }
        let Some(widget) = app.get_webview_window("widget") else { return };
        if widget.is_visible().unwrap_or(false) {
            let _ = widget.hide();
        } else {
            let _ = widget.show();
            let _ = widget.set_focus();
        }
    }).expect("register widget hotkey");
}
```

To keep the app alive when the user closes the dashboard, intercept the close
request and call `hide()` rather than allowing exit. Only do this when that is
the intended product behaviour; otherwise the widget must close with the app.

## Recorder flow: three native windows, three responsibilities

| Window label | Page / React root | Lifetime | Role |
| --- | --- | --- | --- |
| `recorder` | `recorder.html` / `RecorderApp` | reusable | Setup UI, 3-2-1 badge, then recording HUD |
| `area-picker` | `area.html` / `AreaPickerApp` | reusable | Full virtual-desktop drag surface |
| `area-frame` | `frame.html` / `AreaFrameApp` | reusable | Click-through crop outline during recording |

The `area-picker` and `area-frame` windows are created on demand with
`WebviewWindowBuilder`; unlike the ordinary widget they should not be listed
as fixed `tauri.conf.json` windows, because their geometry depends on the
virtual desktop and selected crop.

### End-to-end sequence

1. The recorder calls `pick_capture_area`.
2. Rust hides the recorder, calculates the virtual-desktop rectangle, then
   creates/shows a transparent, borderless, always-on-top `area-picker` window
   covering that rectangle.
3. `AreaPickerApp` records pointer events in its own local logical coordinate
   system. On mouse-up it invokes `complete_area_pick(x, y, width, height)`.
4. Rust adds the virtual desktop origin, chooses the monitor containing the
   selected rectangle's centre, converts the result to that monitor's local
   crop coordinates, clamps it to its bounds, hides the picker, and returns:

   ```rust
   #[derive(Clone, serde::Serialize, serde::Deserialize)]
   pub struct CaptureCrop { pub x: f64, pub y: f64, pub width: f64, pub height: f64 }
   #[derive(Clone, serde::Serialize, serde::Deserialize)]
   pub struct CaptureAreaSelection { pub source_id: String, pub crop: CaptureCrop }
   ```

5. The recorder store retains this selection. Its `start_recording` request
   passes `source_id` and `crop` to the platform capture backend instead of a
   whole-display source.
6. After recording starts, Rust creates/shows the tiny `area-frame` window at
   the crop bounds plus a 3 px outset. It calls `set_ignore_cursor_events(true)`
   so it can never block interaction with the captured app.
7. On stop, cancel, or recorder dismissal, hide the frame and clear the
   selection. Also exclude every product overlay from capture if the OS offers
   that feature; otherwise the recorder HUD/frame may record itself.

Cross-monitor selections must have a stated policy. Capptivo chooses the
monitor containing the selection centre and clamps the crop to it. It does not
attempt to stitch two display streams into one capture.

## Frontend code for the area picker

This is the essential frontend; it draws the translucent selection overlay,
normalizes reverse drags, cancels with Escape, and sends logical coordinates to
Rust. Replace `commands.*` with typed `invoke` wrappers in a new app.

```tsx
import { useCallback, useEffect, useRef, useState } from "react";
import { invoke } from "@tauri-apps/api/core";

type Rect = { x: number; y: number; width: number; height: number };
const MIN = 48;
const rectFrom = (a: {x:number;y:number}, b: {x:number;y:number}): Rect => ({
  x: Math.min(a.x, b.x), y: Math.min(a.y, b.y),
  width: Math.abs(a.x - b.x), height: Math.abs(a.y - b.y),
});

export function AreaPickerApp() {
  const root = useRef<HTMLDivElement>(null);
  const start = useRef<{x:number;y:number} | null>(null);
  const [rect, setRect] = useState<Rect | null>(null);

  const cancel = useCallback(() => { void invoke("cancel_area_pick"); }, []);
  useEffect(() => {
    const onKey = (e: KeyboardEvent) => e.key === "Escape" && cancel();
    addEventListener("keydown", onKey);
    return () => removeEventListener("keydown", onKey);
  }, [cancel]);

  return <div ref={root} className="picker" style={{background:"rgba(0,0,0,.45)"}}
    onPointerDown={(e) => {
      if (e.button !== 0) return;
      root.current?.setPointerCapture(e.pointerId);
      start.current = {x:e.clientX, y:e.clientY};
      setRect({x:e.clientX, y:e.clientY, width:0, height:0});
    }}
    onPointerMove={(e) => { if (start.current) setRect(rectFrom(start.current, {x:e.clientX,y:e.clientY})); }}
    onPointerUp={(e) => {
      if (!start.current) return;
      const chosen = rectFrom(start.current, {x:e.clientX,y:e.clientY});
      start.current = null;
      if (chosen.width >= MIN && chosen.height >= MIN)
        void invoke("complete_area_pick", chosen);
      else setRect(null);
    }}>
    {rect && <div className="selection" style={{left:rect.x, top:rect.y, width:rect.width, height:rect.height}} />}
    <p>{rect && rect.width >= MIN && rect.height >= MIN ? `${Math.round(rect.width)} × ${Math.round(rect.height)}` : "Drag to select · Esc to cancel"}</p>
  </div>;
}
```

```css
html, body, #root, .picker { width: 100%; height: 100%; margin: 0; overflow: hidden; }
.picker { position: relative; cursor: crosshair; user-select: none; touch-action: none; }
.selection { position: absolute; box-sizing: border-box; border: 2px solid #38bdf8;
  background: rgba(56, 189, 248, .10); pointer-events: none; }
.picker p { position: fixed; top: 24px; left: 50%; transform: translateX(-50%);
  color: white; background: rgba(0,0,0,.75); padding: 8px 16px; border-radius: 999px; }
```

Use a non-zero-alpha background on the picker. A completely transparent
WebView can fail hit-testing on macOS. The original production version also
uses pointer capture, a reset event when reusing the picker, and a one-submit
guard so duplicate pointer events cannot start two selections.

Tauri event; after hiding a frame, park it offscreen to prevent an old crop
from flashing during a delayed native-window creation.

## Countdown is a native resize, not CSS centering

The 3-2-1 number is React, but the visible central card is the recorder's
native window resized to 240 × 240 and placed at the active monitor's work-area
centre. At click Record:

```
React: counting=true → prewarm mic/camera → invoke(set_recorder_layout, "countdown")
Rust:  recorder native window → size 240×240 + centre on active monitor
React: Countdown ticks 3 → 2 → 1
React: set layout "hud" first → invoke(start_recording) exactly once
Rust:  backend receives sourceId + crop → area-frame is shown
```

The order `hud` before `start_recording` avoids briefly painting countdown
content in the compact HUD window. The countdown completion must be latched;
React Strict Mode can run effects twice. The original `countdownTick.ts` uses
`{ n, fired }` rather than treating `n === 0` itself as a one-time event.

```rust
#[tauri::command]
fn set_recorder_layout(app: tauri::AppHandle, layout: String) -> tauri::Result<()> {
    let Some(win) = app.get_webview_window("recorder") else { return Ok(()) };
    if layout == "countdown" {
        let (w, h) = (240.0, 240.0);
        let Some(monitor) = win.current_monitor()?.or(app.primary_monitor()?) else {
            return Ok(());
        };
        // Compute from monitor.work_area(), convert logical/physical values using
        // its scale factor, then set the native window's size and position.
        // See `windows.rs` at 09c9bdc for Capptivo's tested helper.
        let _ = (w, h, monitor);
    }
    Ok(())
}
```

## Platform and capture safeguards

- Work in one coordinate system at a time. The picker emits **logical** local
  coordinates. Map to virtual desktop, then to the selected monitor, then
  convert exactly as the recording backend expects. Windows mixed-DPI monitors
  are the common source of wrong crops.
- `alwaysOnTop` is visual layering, not capture exclusion. On Windows, apply
  `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` to the guide/HUD where
  supported. On macOS pass the overlay window IDs to ScreenCaptureKit's
  excluded-targets list. Verify the actual recording has no product chrome.
- A visual guide must be click-through. A fullscreen guide that accepts input
  makes the desktop unusable; Capptivo intentionally uses a small border-only
  window instead.
- Screen recording permissions, portal flow, and capture APIs are platform
  backend concerns. The picker only returns `{ source_id, crop }`; it does not
  record pixels itself.
- Hide the guide on every terminal path: cancellation, start failure, stop,
  close/dismiss, and app shutdown.
